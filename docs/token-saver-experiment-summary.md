# 五个省 Token 工具：实验设计与结果

整理日期：2026-10-12。本文汇总已完成的实验与讨论，用于核查实验和指导日常开发试用。数字以链接的结果报告为准。

## 1. 关键结论

**本次观察到 Caveman 的输出缩减和 RTK 的未缓存输入缩减，但没有足够证据证明某个工具在这些条件下能稳定减少整项开发任务的总用量。**

这不等于五个工具都无效，也不等于它们造成了用量增加。局部缩减能否变成完整任务的收益，取决于实际覆盖范围、任务中的作用机会、模型执行路径和返工；本实验还存在反馈范围与远程测试波动的干扰。

当前可以给出绑定场景的试用建议，不能给出通用排名、普遍节省比例、费用降幅或 Codex 订阅额度节省率。

## 2. 实验的基础设计

### 2.1 要回答的问题

从日常开发出发，回答：

1. 工具是否真的接入并发挥作用？
2. 在有作用机会的开发任务里，是否减少完整工作消耗？
3. 是否保持交付质量，是否增加反馈和返工？
4. 什么场景值得试装，什么时候应该关闭？

不以工具的宣传数字、输出字符数、代码行数或社区关注度代替实际工作效果。

### 2.2 正式范围与共同条件

| 项目 | 条件 |
| --- | --- |
| 执行环境 | Codex CLI 0.158.0 |
| 模型 | `gpt-5.6-sol` |
| 推理强度 | medium |
| 对照 | 同区组 baseline，不组合工具 |
| 重复 | 每项工具比较四次配对，固定轮换顺序 |
| 隔离 | 新位置使用独立副本、私有配置目录和新会话 |
| 多阶段任务 | 同位置沿用自己的工作副本和会话，跨位置独立 |
| 时间与回退 | 无 Agent 执行时间上限，无模型回退 |
| 验收反馈 | 首次交付后最多两轮失败反馈；保留首次成绩及全部成本 |
| 记录原则 | 失败、反馈、未触发和缺失值保留；missing/null 不按 0 处理 |
| 正式比较外 | Cursor、Luna、接入校准与合成探针不混入正式效果比较 |

已核对请求及原生会话中的模型与推理标签；供应商实际解析的后端模型快照未知。

### 2.3 为什么采用不同任务

五个工具的作用路径不同。完全相同的任务可能让部分工具缺少作用机会，因此采用场景匹配：每个工具与相同任务、相同条件下的 baseline 比较，不跨任务排名。

| 场景 | 参与比较 | 作用机会 |
| --- | --- | --- |
| Memos 附件文件名搜索 | baseline／Ponytail | 在真实前端功能中选择复用、平台能力和最小必要实现 |
| HTTPie Cookie 作用域修复 | baseline／Caveman／CodeGraph | 修复过程的模型输出，以及跨文件结构检索 |
| HTTPie 下载诊断到修复 | baseline／Caveman／CodeGraph，历史诊断续接 | 观察解释、修复和反馈的完整成本；配置与新任务分开 |
| HTTPie 三阶段维护 | baseline／RTK／Headroom | gzip 完整下载、分段续传、gzip 续传文件保护；提供命令输出与多轮历史上下文 |

正常接入新任务 20 个位置，历史诊断续接 12 个位置，组成开发决策批次。RTK／Headroom 是另一个独立批次，共 12 个位置、36 个初始阶段。两批不合并为统一排名。

### 2.4 接入方式与实际触发

“安装成功”不等于“实际起作用”，每个正式位置都检查对应证据。

| 工具 | 本次接入 | 触发证据与配置边界 |
| --- | --- | --- |
| Ponytail 4.10.0 | 原生插件 full | 四个新位置均确认 SessionStart Hook 正文加载，无重复目录注入与预算警告 |
| Caveman full | 显式加载项目沟通 Skill | 四个 Cookie 位置均确认正文加载；只测试选定的沟通 Skill |
| CodeGraph 1.6.0 | 新 Cookie 任务使用 CLI；历史续接使用 MCP | 新任务共 15 次 CLI 调用；新副本启用自动同步，历史续接保持父配置，不能混同 |
| RTK 0.49.0 | 自动 Hook 改写普通命令 | 四个位置均实际改写执行；各位置改写／Hook 命令数为 23/32、25/43、14/25、21/32 |
| Headroom 0.39.1 | 原生命名 provider 代理，沿用 ChatGPT OAuth | 四个位置均观察到输出改变；使用固定 `native-offline` 配置 |

RTK 改写次数不等于成功压缩次数。Headroom 改变的独立输出数与请求次数也不能相除当作压缩率。

Headroom 正式配置保留 `keep_last_turns=4` 与默认近期保护，启用 Responses 原文恢复处理；关闭 Kompress 及 fallback、响应缓存、memory、image 等功能。结论只覆盖此配置，不覆盖整个产品。

### 2.5 独立验收是什么

由模型产物之外的检查判断任务是否完成，不采信模型自己说“已完成”。

- 调用前，先用原始源码确认外置任务合同能发现缺陷，再用参考实现确认合同可通过。
- HTTPie 使用原始测试、真实本地 HTTP 合同及外置下载合同；将业务源码移植到干净副本验收，防止修改测试掩盖缺陷。
- Memos 使用自动检查、真实本地服务与合成数据，并检查浏览器中的关键行为。
- 原项目既有失败、额外跳过和补验分别展示；补验不能改写原始成绩或删除模型成本。

Memos 图片真实解码已验证，视频占位文件播放未验证。历史人工复核未盲化的限制保留在原报告中。

### 2.6 用量口径

完整任务 Token 是所有模型回合的输入与输出之和，包含首次失败和后续反馈。

`总 Token = 输入 Token + 输出 Token`

`输入 Token = 未缓存输入 + 缓存输入`

缓存输入是输入的一部分，不能重复相加。多轮反复携带的历史会累积计入总量；总量不是独立文本长度，也不是上下文窗口占用。

输出 Token 指供应商记录的整个模型工作流输出，不能直接等同于最后答复字数；推理 Token 未独立报告时保持未知。

变化中位数采用四个区组中“工具／baseline 比值”的中位数相对 1 的变化，不用先汇总所有样本再相除的方法替代。正数表示增加，负数表示减少。

费用、订阅额度变化、真人配置时间、首次下载构建与长期维护成本未完整测量，不能由 Token 数字推算投资回报。

## 3. 五个工具的实验结果

### 3.1 主结果表

各行只与本行任务的 baseline 比较。四次配对仅提供描述性结果，不代表统计显著性。

| 工具 | 任务 | 总 Token 变化中位数 | 未缓存输入变化中位数 | 输出变化中位数 | 总量更低／更高 |
| --- | --- | ---: | ---: | ---: | --- |
| Ponytail | Memos 附件搜索 | +10.8% | +5.3% | −5.8% | 1/4 ／ 3/4 |
| Caveman | HTTPie Cookie 修复 | −7.8% | +13.5% | −28.7% | 2/4 ／ 2/4 |
| CodeGraph | HTTPie Cookie 修复 | +2.9% | +21.8% | −13.0% | 2/4 ／ 2/4 |
| RTK | HTTPie 三阶段维护 | −3.9% | −22.0% | +3.3% | 2/4 ／ 2/4 |
| Headroom | HTTPie 三阶段维护 | +14.5% | +8.0% | +13.6% | 1/4 ／ 3/4 |

特别需要展示：Caveman 在 Cookie 任务中输出四次均更低；RTK 未缓存输入三次更低；CodeGraph 在 Cookie 任务中未缓存输入四次均更高。

### 3.2 质量与反馈

| 比较组 | 首次通过 | 最终通过 | 反馈轮数 |
| --- | --- | --- | ---: |
| Memos baseline | 4/4 | 4/4 | 0 |
| Ponytail | 4/4 | 4/4 | 0 |
| Cookie baseline | 2/4 | 4/4 | 2 |
| Caveman，Cookie | 4/4 | 4/4 | 0 |
| CodeGraph，Cookie | 3/4 | 4/4 | 1 |
| 三阶段维护 baseline | 4/4 位置全部阶段首次通过 | 4/4 | 0 |
| RTK | 3/4 位置全部阶段首次通过 | 4/4 | 1 |
| Headroom | 3/4 位置全部阶段首次通过 | 4/4 | 1 |

开发决策批次 32 个位置最终通过，首次交付 27/32 通过，本批次共 37 个模型回合；完整历史工作流另外计入原 12 次诊断成本。原诊断质量不因续接成功而改写。

RTK／Headroom 批次 12 个位置最终通过，36 个初始阶段中 34 个首次通过，加两次反馈共 38 个模型回合。最终通过不代表没有返工。

### 3.3 历史诊断续接结果单列

| 工具 | 场景 | 总 Token 变化中位数 | 未缓存输入变化中位数 | 输出变化中位数 | 总量更低／更高 |
| --- | --- | ---: | ---: | ---: | --- |
| Caveman | HTTPie 诊断到下载修复 | +17.7% | +0.3% | −4.3% | 2/4 ／ 2/4 |
| CodeGraph | HTTPie 诊断到下载修复 | −3.1% | +5.6% | +8.5% | 2/4 ／ 2/4 |

Caveman 的 Cookie 输出收益不能直接推广到诊断修复工作流。历史配置与新任务不同，不能把两类结果拼接为一个平均节省率。

### 3.4 RTK／Headroom 的四组波动

| 区组 | RTK 总量变化 | Headroom 总量变化 |
| --- | ---: | ---: |
| 1 | −29.0% | +102.8% |
| 2 | +172.6% | +28.0% |
| 3 | −33.2% | −48.0% |
| 4 | +21.2% | +1.0% |

只报一个中位数会掩盖波动，视频应同时显示“几次降低／几次增加”或配对点图。四次全部降低不是判断工具有效的必要条件；方向混合与大幅波动意味着当前归因和稳定性证据有限。

## 4. 为什么有省 Token 原理，却没有明确的整体收益？

### 4.1 五个工具缩减的是不同部分

| 工具 | 省 Token 的路径 | 当前观察与解释边界 |
| --- | --- | --- |
| Caveman | 压缩交流风格 | 输出缩减已观察到；阅读、工具调用与历史输入仍然存在。输出变短不能自动推导总量下降 |
| RTK | 过滤命令输出 | 未缓存输入有正向信号；实际命令未必全部受支持，短输出即使过滤也可能收益有限 |
| Headroom | 压缩进入模型的工具输出 | 输出改变已观察到；正式近期保护与功能配置限制压缩机会，不能拿无保护重复日志探针对照日常收益 |
| CodeGraph | 用结构查询替代盲目搜索与整文件阅读 | 要减少原本需要的阅读才有收益；若检索没有替代后续阅读，可能增加上下文，但本次尚未证明这是增量的具体原因 |
| Ponytail | 复用、平台能力、最小必要实现 | 依赖模型的实现选择，不直接压缩上下文；代码更少也未必减少理解与验证过程 |

Ponytail 固定版本官方说明也指出：任务的过度实现空间与模型遵循方式影响收益，模型可能花更多 Token 考虑实现选择。本次没有单独测量其思考开销，不能把这当作已证实的原因。

### 4.2 局部缩减会被整体消耗稀释

Cookie 第一组 baseline 总量为 1,440,871 Token，其中输出 17,239 Token，约占 1.2%。

**仅作为比例示例：**假设所有其他部分完全不变，输出减少 30%，对总量的直接影响约为 0.36%。真实工作流还会重复携带历史，模型路径也会变化，不能用这个示例预测实测结果。

RTK 官方也区分终端输出缩减、整个输入缩减与账单缩减；工具本地估算不等于供应商计量。

因此应同时看总量、未缓存输入、缓存输入与输出，不能只挑其中一个指标宣布胜负。

### 4.3 同一任务不会固定模型的执行路径

相同任务、模型和验收条件，并不能固定模型如何完成任务。模型可能选择不同文件、不同测试范围、不同修复步骤及不同调用次数。

本次原生记录去重后，三阶段维护第四组 baseline 执行 26 次命令，RTK 执行 32 次命令。更多调用可能反复携带历史上下文，抵消单次输出缩减。

这证明执行路径不同；不能证明压缩导致更多调用，也不能证明模型丢失信息后绕路。命令次数不是模型请求次数，不能直接据此计算增量 Token。

### 4.4 有两处明确的接入／配置限制

**RTK：命令覆盖不完整。**固定版本 Hook 不改写 `.venv/bin/pytest` 和 `.venv/bin/python -m pytest`，裸命令可以改写。实际模型经常使用带虚拟环境路径的命令，所以不能假设主要测试输出都已过滤。固定版本 `git diff --no-index` 还出现空输出，`rtk proxy` 可以保留原始输出；这是使用限制，不能据此认定正式任务失败由它造成。

**Headroom：测试的是一套有限配置。**近期消息受到保护，Kompress 及 fallback 关闭。此前重复日志从 32,029 字符缩到 175 字符的校准采用取消近期保护的配置，只证明特定重复日志可压缩并保留指定错误，不代表正式维护任务的收益。

正式结果中 RTK、Headroom 均真实触发，不能用早期未接入事故解释后续正式成绩。

### 4.5 实验存在反馈范围和远程测试波动的干扰

RTK、Headroom 各有一次首次失败，涉及 `test_chunked_form`、`test_chunked_json` 的 3 秒远程请求超时。这里的 3 秒来自原测试，不是已取消的 Agent 执行时间上限。

反馈同时列出了三项已知上游失败，可能扩大模型修复范围。随后对未修改的失败快照和固定原始起点做同条件定点检查，四次均通过，支持外部请求波动假设，但不能确定超时原因。

全部反馈成本保留，因为它反映本次实际完成工作的消耗；同时，这些成本不能全部归因于工具。不能删除异常轮来制造节省，也不能把异常轮当作工具增加成本的因果证据。

### 4.6 目前能解释到什么程度

| 证据层次 | 当前判断 |
| --- | --- |
| 已观察 | 局部指标改善、真实触发、命令覆盖限制、Headroom 固定配置、执行路径不同、反馈与测试波动 |
| 合理但未证实的解释 | 新增查询／规则开销、重复阅读、额外调用抵消收益、信息压缩引起补查 |
| 尚不能判断 | 各原因的贡献比例、缓存变化的具体原因、长期费用与额度收益、其他模型和仓库效果 |

四次重复、单一任务和配置不足以分清所有原因。本实验提供端到端描述性结果与试用依据，尚未完成严格的机制归因。

## 5. 从省 Token 角度，哪些值得留下？

| 工具 | 当前可支持的选择 | 适合试用的场景与保留条件 |
| --- | --- | --- |
| Caveman | 按需保留，用于控制输出；不承诺整体省额度 | 类似 Cookie 修复的任务，希望表达简短，同时保留原因、验证与风险；若需要反复补问，应把补问计入成本 |
| RTK | 有条件小范围试装 | 经常使用受支持命令、终端输出长，且 Hook 确实触发；保留关键错误与完整 diff，观察自己的完整任务消耗 |
| CodeGraph | 按结构检索需要选择，当前不以省 Token 为默认安装理由 | 调用链、影响范围和陌生仓库探索；确认查询替代了无效阅读，索引及时同步 |
| Ponytail | 在本附件搜索任务中，不因省 Token 默认启用 | 存在复用或平台能力选择时可以另行试用；不能把代码行数减少当作整体 Token 收益 |
| Headroom | 不因本次维护结果默认启用 | 历史上下文反复携带大量工具输出时，可独立配对试用；核对配置、压缩与质量后再保留 |

这些是条件性建议，不是普遍的“必装／卸载”结论。四次都降低不是硬性门槛；实际使用应综合收益幅度、波动、质量、返工和维护成本。

## 6. 如果继续追查原因，补什么最有价值？

以下是机制归因的后续建议，不是已完成的结果，也不是视频发布的既定前置要求。

1. **固定输出回放：**将相同命令与输出经过工具，记录覆盖率、实际 Token 缩减、错误与关键内容是否保留，区分字符数和 Token。
2. **完整请求分解：**量化受工具影响的内容在每次请求中的比例，以及重复携带次数，解释局部收益为何被稀释。
3. **反馈范围收窄：**仅反馈任务要求与新增失败，将已知上游失败分列；保留原批次，不修改历史数字。
4. **增加代表性任务：**包括长测试输出、陌生仓库结构探索、重复历史输出、明显存在平台复用选择的功能，仍与各自 baseline 比较。
5. **验证路径变化：**结合调用记录检查补查、重复阅读与返工，避免仅靠命令次数推断信息丢失。

固定回放用于验证局部机制；自然执行用于判断真实工作收益。两种证据结合，才更有把握区分能力、作用机会与工作流成本。
