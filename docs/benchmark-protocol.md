# Token Saver Bench：实验设计与运行协议

协议版本：v4（2026-10-09，Codex 单环境草案）。本文档是实验设计的**单一权威规范**，操作指引见[复现指南](reproduction-guide.md)。

> **本期执行方案**：实验问题为“省 Token 工具，什么情况下值得试装？”。正式范围仅有 Codex CLI＋GPT-5.6 Sol／medium，下载诊断 baseline／Caveman／CodeGraph 与 Memos 功能 baseline／Ponytail，各组 4 次，共 20 个位置、20 次调用。首次交付，无修复反馈，无执行时间上限。RTK 自动改写未触发，Headroom 请求代理未接入，二者保留为接入未能测量；三阶段比较暂缓。新正式入口在核对真实证据及当前身份后冻结计划才能启动；历史计划未冻结时不能调用模型。Cursor 仅保留历史记录。

## 1. 核心研究问题

面向使用 Codex CLI 的开发者，给出可复现的配置、适用条件与安装后的检查方法。按场景回答以下问题，不产生跨任务的通用冠军：
1. **真省了吗（Token）**：在相同任务与模型下，工具是否真正减少了供应商记录的 `total_tokens` 与非缓存输入？
2. **质量降了吗（Quality）**：代码是否依然正确、健壮，是否破坏了既有项目测试？
3. **耗时如何（Time）**：指令注入或额外代理是否导致交互轮次增加或进程超时？
4. **接入证据（Activation）**：工具是真正生效了，还是根本未触发？（未触发必须如实记录，不能伪装成有效）。
5. **值得试装吗**：收益需要什么工作负载、配置与人工操作？首次接入和后续维护的成本是否可接受？

官方描述只用于确定机制和场景假设，供应商用量与独立验收才用于判断效果。一次前端任务或 CLI 任务不能代表整个前端或后端领域。

*注：在缺乏服务商逐笔官方账单明细前，费用（USD）一律保持 `null`，严禁通过套餐价格反推虚构。*

- **人工介入**：校准可以显式调用来确认机制；正式运行采用预注册的正常接入，不临时催促 Agent 使用工具。额外提醒或配置修改须保留记录，不能混入原方案。

- 选题满足官方机制支持、真实日常工作负载与独立可验收三项条件。记录日常触发条件与使用频率的适用前提，不编造总体用户频率。
- 不以正式成绩选择参与组或改题。校准证明没有机会时，记录原因；需要补题就在正式前冻结，已经启动的样本不得重新归类以改善成绩。
- 本期先观察**首次交付**。失败标记**返工成本未测**，不能作为“完成合格需求更省”的证据。若增加修复阶段，正式前为各组冻结同一反馈规则、机会数、预算和停止条件，保留首次失败并报告累计用量；目前未启用修复。

## 4. 调度、校准与预算

### 4.1 偏倚控制逻辑
按场景安排区组，交错顺序用于降低时间、网络和**服务端 Prompt Cache 偏倚**，不能保证消除偏差：
- 同一区组内，各工具组与该区组的原生 baseline（A）配对。
- 每个正式场景计划 4 个重复区组，预先保存具体执行顺序及生成规则，在可行范围内交错位置；缺少运行或配对时如实披露。
- 保存开始时间、缓存分项、原生压缩事件和中断间隔。原生能力保持一致，非被测因素不得只在某工具组关闭。

### 4.2 本期正式规模与身份冻结

- 本期 Codex 首次交付位置数为：各场景 `4 × (1 + 参与工具数)` 之和，再加单独冻结的共同任务补充位置。连续迭代的一个位置可含多个模型执行阶段，位置数不能冒充模型调用次数。
- 正式预算同时列出位置、阶段、预计执行次数及最大时间；费用未知保持 null。修复或补充任务若启用，单独计入。
- 旧版两题全六组方案的 **48 次/环境、96 次/两环境** 已不再作为当前计划，不是新的预算承诺。
- **当前执行子集**仍为 **16 个位置**（Codex CLI 下 Memos 与 HTTPie 各 4 对 baseline / Ponytail 的 AB/BA 交错运行），仅用于已有准备能力的预览；不是本版本正式调度。
- 本期正式清单为诊断 12 个位置与 Memos 8 个位置，合计 20 次新调用。RTK／Headroom 排除证据和三阶段暂缓理由进入冻结计划；不执行无工具对照的三阶段 baseline。校准的质量失败不要求通过后重试，正式质量独立评分并原样报告。
- 使用 `node bin/campaign.js plan <readiness.json>` 预览，`start` 核对私有证据的 SHA-256、当前预检与冻结身份，随后串行执行。这里的门槛就绪表示计量、隔离、机制与验收方法可用，不表示模型产物合格。旧 `bin/real-development.js start` 继续关闭。

### 4.3 正式启动门槛

固定工具版本、环境及计量方式 → 冻结场景任务和参与组 → 校准接入、作用机会及验收器 → 冻结完整调度与预算 → 完成运行器并检查 → 才可正式启动。校准、历史试跑与事故样本保留独立身份，不进入正式效果统计；新增模型校准调用也消耗额度，须在启动前列入计划。

## 5. 判卷隔离与防作弊机制

为保证评测客观，杜绝 Agent“篡改测试以伪造通过”：
1. **独立临时沙箱**：每次调用在 `/tmp` 独立目录由 Git 干净检出，运行后保留归档。
2. **编码场景源码单向移植（Transplant）**：
   - 判卷不在 Agent 工作目录内进行。
   - 验证器新建纯净副本，**仅将 Agent 产出的业务源码单向移植过去**（Memos 为 `web/src`，HTTPie 为 `httpie`）。
   - **关键防作弊效果**：Agent 修改或删除单元测试的行为完全无法污染独立判卷环境。
3. **非编码场景**：以固定原始源码或补丁独立核对回答，保留原回答与引用证据，不以空补丁或原项目测试通过代替答案验收。

## 6. 指标计算与停止条件

### 6.1 Token 指标算式
- **总 Token**：$\text{total\_tokens} = \text{input\_tokens} + \text{output\_tokens}$。
- **非缓存输入**：$\text{uncached\_input\_tokens} = \text{input\_tokens} - \text{cached\_input\_tokens}$（缓存输入已包含在 input 内）。
- **缺失值处理**：未返回时保持 `null`，严禁记为 0。无账单时 `actualCostUsd = null`。

### 6.2 质量四层级判定
1. 外置黑盒合约测试通过。
2. 既有项目测试套件通过（宽回归无新增失败）。
3. 静态检查（类型检查、Lint、构建）通过。
4. 人工浏览器复核（未复核前标为 `pending`，不得虚报质量通过）。

编码场景按上述四层执行，具体工具链和人工项随任务冻结；非编码场景采用事实核对、关键约束与匿名可读性复核，不能以未运行代码构建虚报质量。人工记录使用匿名组号，未盲化须披露。

### 6.3 作用机会与接入成本

- 分别记录“缺少作用机会”“有机会但未触发”“发生处理”“证据不足”和“未能测量”。输入字节或工具估算 Token 仅作诊断，不替代供应商用量。
- 记录命令原始/处理后输出量、检索调用、上下文长度与内容类型、压缩/原文取回、重复执行和人工提醒。规则注入的可核对证据不等于行为遵从。
- 单列首次安装配置、索引构建/同步、代理启动、任务期间附加时间、资源需求和后续维护。计时外准备可用，但必须披露；首次与准备完成后的使用成本不混算。
- 若用量接口无法区分用户可见回答、推理或其他输出分项，缺失保持 null，不用文本长度推算供应商 output。

### 6.4 熔断与留痕规则
- **熔断停机**：检测到 API 额度耗尽（`quota`）、限流（`rate-limit`）或环境漂移，立即停止后续调用并生成 `stopped.json`。
- **全量留痕**：失败、超时、未触发样本永久保留，**严禁用“重新跑一次成功”替换失败记录**。
- **报告原则**：按“Codex CLI × 任务 × 工具”矩阵如实报告，不宣扬小样本统计显著性，给出有明确前置条件的安装建议。

## 7. 报告与视频结论规则

- 按“Codex CLI × 场景 × 任务 × 配置”展示全部运行身份、质量、供应商用量、时间与作用机会；主实验和共同任务补充检查分开。
- 报告首次通过次数、有效配对数、每次配对差值、中位数及范围。只有双方质量合格且对应指标完整的配对，才用于同质量用量比较；未通过、缺失和不成对样本仍在全量表中，不当作节省，不静默丢弃。
- 总输入、缓存输入、非缓存输入、output 与总 Token 分别展示，指标方向不一致时说明；不推算订阅账单收益。四次重复只支持初步观察，不宣称统计显著或长期稳定。

| 结论 | 所需证据与措辞 |
| --- | --- |
| 值得优先试装 | 有实际作用、质量满足预注册条件、配对结果支持收益且没有未解释的重大代价；绑定环境、版本、配置、工作负载、使用频率前提与安装成本。仅为本次证据支持的试装建议 |
| 有收益也有代价 | 用量下降但质量、信息保留、可读性、时间或维护有损失，或配对结果方向波动；同时展示代价，不给无条件推荐 |
| 本次证据不足 | 无作用机会、未触发、无法计量、质量待复核或样本不足；分别说明原因，不把 null 当 0、不把未触发判为无效 |
| 本次未观察到收益 | 有作用且可计量，但该场景未支持收益；保留完整结果，不推广为工具在全部任务无效 |

视频围绕“常见消耗 → 真实场景证据 → 可照做的配置与检查”组织。不要求每个工具都得到推荐，不根据结果修改预注册场景。可选最有解释力的案例展示，但需说明选择理由并提供完整结果表；结果分歧时展示分歧，不能概括为普遍前端/后端规律。实际未公开前不声称“都开源了”。

### 8.3 真实会话与计量校准的验收条件

真实校准调用消耗额度，当前离线入口不执行这些调用。开始前固定模型、推理强度、调用次数与预算，并将校准产物单独记录。

- **会话续接**：同一位置在三个独立 CLI 进程中使用同一私有状态目录和明确 thread ID；核对实际状态记录、阶段输入与前序信息可用性。另一个位置使用全新目录和会话，不能读到前一个位置的信息。仅回答前序内容或仅 thread ID 相同不足以完成校准。
- **身份与隔离**：记录实际解析出的模型、CLI 版本、配置来源及状态位置；认证方式需显式准备，不复制用户整个全局目录。身份无法核对时保留 unknown，不记为已校准。
- **计量口径**：保留每个进程原始终端事件，与同一会话的本地实际 usage 记录核对；确认计数是 per-turn 还是累计值，再冻结归一化规则。解析器已支持明确累计口径的差分；续接缺少前值时返回 null，计数回退或差分缓存超过输入时拒绝。未知口径不能强行相加。
- **异常与重复**：实测缺失 usage、重复终端、会话漂移、超时及额度／限流的保存和停止行为；缺失不填 0，失败样本不删除。缓存 Token 属于输入，费用缺失保持 null。
- **工具作用**：逐工具核对真实宿主触发路径及场景内作用机会，不能以规则注入、模拟 hook 或代理自报替代触发证据。校准通过后再冻结参与组和正式预算。
